# ADR-004 — Seguridad por rol con Spring Security

| Campo | Valor |
|---|---|
| Estado | Aceptado |
| Fecha | 13 de noviembre de 2026 |
| Decisores | Kevin Andréy Flórez Ramírez y Juan Miguel Corales |
| Requisitos | REQ-ZAP-001 a REQ-ZAP-010, REQ-ZAP-028, REQ-ZAP-031, NFR-ZAP-002, NFR-ZAP-005 |
| Relacionado | ADR-001, ADR-002 |

## Contexto

El sistema tiene cinco roles y rutas muy distintas: administración de usuarios, catálogo, inventario, carrito, ventas, gestión de pedidos, facturas y reportes. Un cliente no puede ver pedidos ajenos; un almacenista no puede confirmar pedidos; solo el gerente genera el reporte. Además, las contraseñas deben cifrarse y no deben aparecer en logs.

## Decisión

1. Se usa Spring Security con autenticación por correo y contraseña.
2. Cada ruta declara sus roles en `SecurityConfig`; lo no declarado exige sesión iniciada.
3. Los permisos finos se validan en el controlador o en la entidad: dueño del pedido, última cuenta de administrador, estado facturable, transición válida.
4. Las contraseñas se cifran con `BCryptPasswordEncoder` y cumplen la política de 8 caracteres con letra y número.
5. CSRF permanece activo; los formularios incluyen el token y las pruebas usan `csrf()`.
6. El login falla con el mensaje genérico «Correo o contraseña incorrectos», sin distinguir correo inexistente, clave incorrecta o cuenta inactiva.
7. Ninguna clave se escribe en logs; `DatosIniciales` solo informa los correos de demostración.

## Consecuencias positivas

- La autorización es declarativa y fácil de auditar.
- El menú y las acciones se ocultan con `sec:authorize`, pero la decisión real ocurre en el servidor.
- Un rol no autorizado recibe 403, no una página vacía.
- Las pruebas cubren login, logout, cuenta inactiva, 403 y último administrador.

## Consecuencias negativas

- `SecurityConfig` debe actualizarse cada vez que se agrega una ruta; una ruta olvidada queda solo con sesión, no con rol.
- La autorización fina duplica parte de la lógica en controladores.
- El mensaje genérico dificulta el soporte, aunque es el comportamiento requerido.

## Alternativas consideradas

1. **Solo anotaciones `@PreAuthorize`.** Válido, pero dispersa la configuración y dificulta ver el mapa completo. Se prefiere la cadena central con refuerzo puntual.
2. **Sesiones JWT.** Innecesario para una app server-side con sesión HTTP. Se descarta.
3. **Ocultar botones sin proteger la ruta.** Inseguro; se descarta.

## Cumplimiento

- `SecurityConfig` define login, logout, CSRF y reglas por ruta.
- `UsuarioController` impide desactivar al último administrador.
- `PedidoController` y `FacturaController` verifican la propiedad del pedido.
- `TiendaIntegracionTest` prueba AC-001.1, AC-002.1, AC-002.2, AC-003.1, AC-008.1 y AC-009.1.
- `DatosIniciales` ya no registra la clave demo.
